# AI Battle CyberSec — агент для задач кибербезопасности

Создайте универсального агента, который решает задачи КБ. Модели, провайдеры,
обвязку запуска, инструменты, инструкции, skills вы выбираете сами.

В финале **ваша версия решения** используется на пяти закрытых
задачах: трёх усложнённых аналогах демонстрационных задач, анализе сетевого дампа и анализе
бинарного файла. Для каждой задачи собирается отдельный Docker-образ с обвязкой
участника и материалами этой задачи.

## Материалы конкурса

Публичный репозиторий условия с исходными
материалами.

В `tasks/` находятся **демопримеры задач для подготовки**. В финальной проверке
будут три аналогичные, но усложнённые задачи с другими исходными данными,
а также две задачи по заранее известным направлениям: **анализ сетевого дампа**
и **анализ бинарного файла**. Обвязка должна предусматривать решение задач
всех пяти направлений по их условию и предоставленным материалам.

```text
README.md
tasks/
  incident/
    task.md
    infrastructure.md
    data/
  access-control/
    task.md
    project/
  config-audit/
    task.md
    manifest.json
    project/
```

| Демо | Материалы |
|---|---|
| [Расследование инцидента](tasks/incident/task.md) | Журналы приложения, аутентификации и reverse proxy |
| [Анализ безопасности кода](tasks/access-control/task.md) | Python HTTP-сервис, описание поведения и функциональные тесты |
| [Аудит конфигураций](tasks/config-audit/task.md) | Dockerfile, Compose, Nginx, сервис записей и контракт развёртывания |

Все материалы синтетические.

Два дополнительных направления финальной проверки:

- **Анализ сетевого дампа:** исследование трафика и поиск признаков подозрительной
  активности с подтверждением по пакетам и соединениям.
- **Анализ бинарного файла:** декомпиляция и последующий анализ псевдокода
  на предмет опасного поведения или уязвимостей.

В финале будет по одной задаче каждого из этих двух направлений. Демопримеры
для них в `tasks/` не предоставляются. При проектировании обвязки предусмотрите
выбор подходящих инструментов и способа анализа для новых условий и входных
данных в объявленных направлениях. Как это реализовать через возможности
выбранного harness, определяет участник.

## Что сдавать

Решение — **отдельный Git-репозиторий с обвязкой агента и Dockerfile**.
Обвязка (harness) — выбранная участником среда работы агента с её настройками,
инструкциями и инструментами. Можно использовать готовый OpenCode, другой
агентный инструмент или собственную реализацию. Писать собственную программу
запуска не обязательно: достаточно установить выбранный инструмент в Dockerfile,
добавить настройки и указать команду его запуска.

На все задачи сдаётся **одна универсальная обвязка агента с общей командой
запуска**. Как реализовать универсальность, определяет участник с учётом
возможностей выбранного harness: через skills, субагентов (subagents),
инструменты, маршрутизацию между моделями или иные механизмы. Эти механизмы
необязательны; внутри общей обвязки могут быть специализированные компоненты
для разных типов задач. Обвязка сама выбирает способ решения по условию
и входным материалам. Вручную выбирать отдельную обвязку, менять инструкции
или команду запуска под конкретную задачу нельзя.

Пример репозитория участника:

```text
README.md                 # точные команды сборки и запуска, доступы и квоты
Dockerfile                # установка выбранного harness, COPY настроек и задачи
.dockerignore             # состав контекста сборки
submission.json           # модели, переменные окружения и команда запуска
harness/
  opencode.json           # пример настроек для OpenCode; формат зависит от harness
  ...                     # инструкции, skills, субагенты, инструменты и свой код при необходимости
```

Сам harness и его зависимости устанавливаются в образ при сборке. В `harness/`
разместите файлы своего решения: настройки, инструкции, skills и другие нужные
материалы. **Содержимое `harness/` копируется непосредственно в `/battle/`,
включая скрытые файлы и папки.** Сохраните структуру, которую выбранный harness
ожидает в текущем каталоге проекта. Собственный код добавляйте, если он нужен
выбранному подходу.
В README решения укажите **команду запуска выбранного инструмента через
`docker exec`**. Например, OpenCode можно запустить напрямую:

```sh
docker exec --workdir /battle ai-battle opencode run \
  "Прочитай task/task.md. Реши задачу по материалам task/. Сохрани результат в единственном файле output/report.md."
```

Здесь `ai-battle` — имя запущенного контейнера, `opencode run` — команда готового
harness, а текст в кавычках — общий запрос для любой задачи. Harness запускается
из `/battle`: в этой папке лежат настройки и инструкции из `harness/`, а рядом —
`task/` с задачей. Параметр `--workdir /battle` явно задаёт текущий каталог процесса;
относительные пути `task/` и `output/` в запросе отсчитываются от него.
OpenCode должен
быть установлен в образе; модель, инструкции и разрешения инструментов участник
настраивает заранее. Запуск должен работать без диалога с человеком.
Отдельные `main.py` или `run-agent` не требуются. Для другого harness укажите
его команду без интерактивного режима; собственный скрипт запуска тоже допустим.
Код возврата `0` означает штатное
завершение, ненулевой — ошибку; полноту ответа и ограничения укажите в `report.md`.
Одна и та же команда должна работать для всех задач. Предметные подсказки извне
не передаются.

При сдаче передайте:

1. URL репозитория и точный commit SHA; организаторам нужен доступ на чтение.
2. Путь к Dockerfile и инструкцию сборки по схеме ниже.
3. Команду запуска обвязки через `docker exec`.
4. Декларацию моделей, внешних сервисов, нужных ключей и квот.

Зависимости и внешнюю обвязку закрепите по версиям; базовый образ для финала
закрепите по digest. После фиксации commit решение менять нельзя.

Пример структуры `submission.json` (значения замените своими):

```json
{
  "models": [{"provider": "PROVIDER", "model": "MODEL"}],
  "required_env": ["ANTHROPIC_API_KEY"],
  "external_services": [],
  "dockerfile": "Dockerfile",
  "build_context": ".",
  "workdir": "/battle",
  "command": [
    "opencode", "run",
    "Прочитай task/task.md. Реши задачу по материалам task/. Сохрани результат в единственном файле output/report.md."
  ]
}
```

Укажите все модели, внешние сервисы, версии инструментов и имена обязательных
переменных окружения в декларации или README. Значения ключей в Git и образ
не включайте. В разработке используются ваши ключи, в финале — ключи организаторов.
API-ключ передаётся **при запуске**, например через `docker run --env ANTHROPIC_API_KEY`;
последующий `docker exec` получает окружение контейнера. Для модели ключ не нужен
на этапе `docker build`: не записывайте его в Dockerfile через `ARG` или `ENV`
и не передавайте через `--build-arg`.

## Как устроен запуск

Организатор берёт зафиксированную версию репозитория и готовит отдельный
каталог сборки для одной задачи:

```text
build-context/
  Dockerfile              # из репозитория участника
  .dockerignore           # из репозитория участника
  harness/                # настройки и материалы решения из репозитория участника
  task/                   # одна задача, добавленная организатором
    task.md
    ...
```

`task/` не нужно добавлять в репозиторий решения. Для демо его содержимое берётся
из каталога выбранной демозадачи, в финале — из закрытых материалов организатора.
Проверки, эталоны и остальные задачи в этот каталог сборки не попадают.
Значение `build_context: "."` в декларации относится к этому подготовленному
каталогу, из которого выполняется сборка.

Далее выполняются три шага:

1. `docker build` устанавливает выбранный harness и зависимости, копирует содержимое `harness/` в `/battle/`, а задачу — в `/battle/task/`.
2. `docker run -d` запускает контейнер в фоне и подключает каталог результатов.
3. `docker exec --workdir /battle` запускает указанную участником команду решения задачи из `/battle`, где находится папка `task/`.

Файлы решения и задача **копируются через `COPY` при сборке**. Например, если
в `harness/` участника находятся `GIGACODE.md` и `.gigacode/skills/`, структура
внутри контейнера после запуска будет такой:

```text
/battle/
  GIGACODE.md
  .gigacode/
    skills/
      skill_example/
        SKILL.md
  task/
    task.md
    ...
  output/
```

Дополнительной папки `/battle/harness/` нет: файлы инструкций и скрытые каталоги
выбранного harness находятся прямо в его текущем каталоге `/battle/`.
При `docker run` подключается только каталог результатов. Сборка готовит
окружение; читать и решать задачу нужно после запуска команды через `docker exec`.
Справка Docker: [`COPY`](https://docs.docker.com/reference/dockerfile/#copy),
[`docker exec`](https://docs.docker.com/reference/cli/docker/container/exec/).

### Пример Dockerfile для OpenCode

Docker нужен для подготовки воспроизводимого окружения: участник выбирает
базовый образ и заранее устанавливает harness, зависимости и утилиты для задач.
Схему размещения кешей, временных файлов и выполнения команд определяет
выбранный harness и настройки участника.

Ниже пример с готовым OpenCode, без собственной программы запуска.
Замените `X.Y.Z` на выбранную точную версию пакета `opencode-ai` и добавьте
системные инструменты, необходимые вашему решению. Для другого harness
замените установку и настройки, сохранив расположение каталогов и запуск
через `docker exec`.

```dockerfile
FROM node:24-bookworm-slim

RUN npm install --global opencode-ai@X.Y.Z

# Копируем содержимое, включая скрытые файлы и папки, прямо в каталог запуска.
COPY harness/ /battle/

# Задачу добавляет организатор в каталог сборки перед docker build.
# COPY идёт после установки зависимостей, чтобы смена задачи не сбрасывала их кеш.
COPY task/ /battle/task/
RUN mkdir -p /battle/output

WORKDIR /battle
# Контейнер ждёт; обвязку запускают отдельной командой docker exec.
CMD ["sleep", "infinity"]
```

`WORKDIR /battle` задаёт текущий каталог запуска, а `HOME` остаётся обычным
домашним каталогом пользователя контейнера. В этом примере используется
стандартный пользователь базового образа — root с домашним каталогом `/root`.
Создавать отдельного пользователя и группу для этого примера не требуется;
участник может настроить их в своём Dockerfile, если это нужно его решению.
Пользователь при `docker run` принудительно не меняется.

В `harness/opencode.json` укажите модель и настройки выбранной версии OpenCode:
в образе этот файл будет находиться в `/battle/opencode.json`. Папка
`harness/.opencode/`, если она используется, попадёт в `/battle/.opencode/`.
Настройте разрешения так, чтобы решение не ожидало подтверждений человека. Если нужны инструкции,
skills или субагенты, подключите их средствами выбранного harness.
См. документацию OpenCode: [установка](https://docs.opencode.ai/docs/),
[настройки](https://docs.opencode.ai/docs/config/),
[запуск через `opencode run`](https://docs.opencode.ai/docs/cli/#run).

Пример `.dockerignore`, разрешающий только файлы решения и одной задачи:

```dockerignore
**
!Dockerfile
!.dockerignore
!harness/
!harness/**
!task/
!task/**
```

Не храните секреты в `harness/`: этот каталог целиком попадает в образ.

| Каталог в контейнере | Назначение |
|---|---|
| `/battle` | Текущий каталог при запуске harness; содержит файлы из `harness/`, включая скрытые папки, а также `task/` и `output/` |
| `/battle/task` | Условие и материалы одной задачи из образа |
| `/battle/output` | Единственный итоговый файл `report.md` |

Файловая система контейнера доступна для записи. Агент может создавать файлы
в каталоге проекта, домашнем каталоге, `/tmp` и других доступных ему местах.
Кеши и внутренние временные каталоги harness работают по его обычным настройкам;
специальный каталог для промежуточной работы не задаётся.
Итоговый отчёт сохраняйте в `/battle/output/report.md`: из контейнера забирается
именно этот файл. Рабочие копии, логи и промежуточные файлы храните вне output.
Для каждой задачи создаётся новый контейнер; изменения в остальных каталогах
между задачами не сохраняются.

## Локальный запуск

Ниже запуск примера с OpenCode; команды выполняются **из корня репозитория
решения** в Bash или Zsh. OpenCode и модель уже должны быть настроены участником.
Укажите абсолютный путь к демозадаче из материалов конкурса. Каждый запуск
создаёт новый каталог сборки и результатов:

```sh
TASK_DIR=/absolute/path/to/ai_battle/tasks/incident
BUILD_DIR=$(mktemp -d)
OUTPUT_DIR=$(mktemp -d)
LOG_DIR=$(mktemp -d)
CONTAINER_NAME="ai-battle-$$"

cp Dockerfile .dockerignore "$BUILD_DIR/"
cp -R harness "$BUILD_DIR/harness"
cp -R "$TASK_DIR" "$BUILD_DIR/task"

read -s ANTHROPIC_API_KEY
export ANTHROPIC_API_KEY

docker build --platform linux/amd64 -t ai-battle-agent:local "$BUILD_DIR" && \
docker run -d --rm --name "$CONTAINER_NAME" --platform linux/amd64 \
  --cpus 4 --memory 8g --memory-swap 8g \
  --mount "type=bind,src=$OUTPUT_DIR,dst=/battle/output" \
  --env ANTHROPIC_API_KEY \
  ai-battle-agent:local && \
docker exec --workdir /battle "$CONTAINER_NAME" \
  opencode run \
  "Прочитай task/task.md. Реши задачу по материалам task/. Сохрани результат в единственном файле output/report.md." \
  > "$LOG_DIR/harness.stdout.log" 2> "$LOG_DIR/harness.stderr.log"
RUN_EXIT_CODE=$?

# Результаты и журналы сохраняются и при ошибке обвязки.
docker stop "$CONTAINER_NAME"
unset ANTHROPIC_API_KEY
echo "Код завершения запуска: $RUN_EXIT_CODE"
echo "Отчёт: $OUTPUT_DIR/report.md"
echo "Журналы запуска: $LOG_DIR"
```

Замените путь к задаче, имя переменной ключа и команду после `docker exec`
на свои. Для других демо укажите `tasks/access-control` или `tasks/config-audit`
в `TASK_DIR` и повторите все шаги с новым каталогом сборки. При сборке каждой
следующей задачи используется та же версия решения и Dockerfile.
`CMD ["sleep", "infinity"]` удерживает контейнер запущенным для `docker exec`.
По завершении команды контейнер сам не останавливается: для этого в примере
есть `docker stop`; `--rm` удаляет его после остановки.

Демо аудита можно решать статически без Docker внутри агента. Доступ к Docker
socket хоста агенту не предоставляется.

## Формат результатов

Для любой задачи результат — **единственный файл `output/report.md`**
в свободной форме. Материалы и цель анализа описаны в `task/task.md`.
Структуру отчёта и способ обоснования выводов участник выбирает сам.

Патчи, тесты и команды не обязательны. Полезные предложения по исправлению,
проверки и способы повторить анализ могут принести дополнительные баллы
по критерию практической проработки.

При незавершённом решении сохраните доступную часть: она тоже оценивается.
В output должен находиться только `report.md`; рабочие копии проекта, логи
и промежуточные файлы храните вне него.

## Условия и оценка

- На задачу — **30 минут с запуска команды через `docker exec`**, включая
  скачивания во время решения и работу субагентов. Сборка подготавливает
  окружение и в это время не входит; анализировать задачу при сборке запрещено.
- Linux amd64, **4 vCPU, 8 ГБ RAM, 20 ГБ записываемого диска**, без GPU.
- Интернет разрешён; человек после запуска не участвует.
- Каждая задача выполняется в чистом окружении. Проверки и эталоны недоступны агенту.
- Один зачётный запуск. Подтверждённый сбой инфраструктуры организатора или
  провайдера допускает повтор; ошибка решения и тайм-аут — нет.

Финал — **5 задач по 20 баллов**, максимум 100. Каждую задачу сначала оценивают
по шкале 100: до 60 за анализ и до 40 за дополнительную практическую проработку,
затем делят на 5. Частично верные результаты получают частичные баллы.
При равенстве итогов сравнивается суммарное время пяти запусков;
при полном равенстве место делится. Стоимость API учитывается отдельно
и на рейтинг не влияет.

Отчёт независимо оценивают два проверяющих, берётся среднее:

| Критерий | Максимум | Что оценивается |
|---|---:|---|
| Корректность | 30 | Верно ли установлены проблемы или события, их причины, условия и последствия |
| Полнота | 18 | Насколько полно решена поставленная задача по предоставленным материалам |
| Обоснованность | 12 | Подтверждаются ли выводы данными, отделены ли факты от предположений |
| Практическая проработка | 40 | Насколько полезны и обоснованы дополнительные исправления, проверки или способы повторить анализ |

Допускаются промежуточные оценки с обоснованием. Пустой отчёт — 0 баллов.
Патчи, тесты и команды — возможные способы получить баллы за практическую
проработку; их формат и наличие не являются условием приёма ответа.
Само наличие таких материалов баллов не приносит: оцениваются их корректность
и польза для задачи. Предложенные исполняемые материалы могут проверяться
отдельно от агента, без API-ключей и доступа к системе оценивания.

Организаторы фиксируют commit SHA, Dockerfile, зависимости и команду запуска.

и одной новой задачей, собирают образ и выполняют `docker run` и `docker exec`.
