# Сервис записей: контракт развёртывания

Локальный стенд требует Docker Engine и Compose v2+. Python 3.12 и Nginx 1.28
используются как фиксированные версии стенда; анализ CVE вне задания.

## Границы и штатное поведение

Сервис `proxy` — единственная точка входа клиентов. Порт на машине задаёт `PORT`
(по умолчанию 18080). HTTP моделирует участок после внешнего TLS-терминатора,
который в стенд не входит. Развёртывание должно слушать только `127.0.0.1`,
без доступа из локальной сети машины.

| Запрос через proxy | Поведение |
|---|---|
| `GET /health` | Без пароля, 200 и JSON `{"status":"ok"}` от приложения |
| `GET /api/records` | HTTP Basic: без пароля или с неверным — 401; с верным — 200, JSON с массивом `records` |
| `POST /api/records` | Та же аутентификация; JSON `{"text":"..."}` создаёт запись, 201; пустой или некорректный текст — 400 |

Тестовая учётная запись: **demo / demo-battle-2026**, файл `nginx/users.htpasswd`.
Это намеренно открытая фикстура. Аутентификацию выполняет Nginx, приложение
получает проверенные запросы по внутренней сети Compose.

Любые другие пути через proxy должны возвращать 403 или 404, в том числе при
верных учётных данных. Query string не меняет политику доступа к маршруту.
Служебный интерфейс приложения предназначен только для диагностики внутри
контейнера и не должен быть доступен клиентам через proxy или отдельный порт.
Каталог `ops/` содержит материалы оператора, необходимые вне клиентского
интерфейса; его файлы не должны раздаваться клиентам. Он не нужен приложению.

Приложение слушает `app:8000`, хранит записи в `/var/lib/records/records.json`
на постоянном именованном томе Compose. Данные должны сохраняться после пересоздания контейнера.
Сервису достаточно обычного непривилегированного UID, записи в свой том и
сетевого соединения с proxy. Доступ к Docker Engine и файлам хоста ему не нужен.
Внешних сервисов и базы данных нет. Входной JSON ограничен приложением 16 КиБ.

Не меняйте код и данные ради соответствия контракту. Можно менять сети, тома,
полномочия и настройки запуска, сохраняя поведение и хранение. Исправления
должны работать с новым пустым томом и томом от исправленного проекта.

## Проверка рабочей копии

Сначала проверьте конфигурации статически и внесите необходимые изменения.
Далее из исправленного `project/`:

```sh
docker compose config --quiet
docker compose build
docker compose up -d --wait app
docker compose run --rm --no-deps proxy nginx -t
docker compose up -d --wait
python3 -m unittest discover -s tests -v
docker compose stop proxy
docker compose up -d --force-recreate --wait app
docker compose start proxy
python3 -m unittest discover -s tests -v
docker compose down
```

Для полного удаления данных после проверки: `docker compose down -v`.
Для проверки постоянного хранения `-v` не добавляйте: создайте запись,
пересоздайте app и проверьте её наличие тем же API.

Публичные тесты проверяют штатный API, но не полноту аудита. Для другого порта
задайте одинаковые значения: `PORT=19080` перед запуском Compose и
`RECORDS_BASE_URL=http://127.0.0.1:19080` перед запуском тестов.

Без Docker выполните статический анализ и приведите команды проверки стенда
в отчёте. Отдельный запуск приложения не проверяет Compose, Nginx и границу
аутентификации; он не заменяет проверку исправленных конфигураций.
